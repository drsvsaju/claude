## Phase 1 — bug fixes
### 1a. Recently used chips — root cause and fix
Root causes (all confirmed in code): (1) `recent` and `pinned` were two whole arrays, uploaded whole and overwritten
whole by `applyProfile` on every snapshot that was not flagged as a local edit; (2) `pushProfile` cleared
`localEditPending` BEFORE its "the cloud copy is not loaded yet" early return, so a star or a block started during the
cache-first load was wiped by the first snapshot; (3) no per-item stamps or tombstones, so two devices simply
overwrote each other (last writer wins, un-pins came back); (4) chips of presets deleted on another device were never
pruned, so a tap loaded the name but kept whatever preset was active; (5) the list could hold near-duplicates.
Fix: one synced list `S.chips` `{ id: 'c:<presetId>:<name lower>', name, presetId, ts, fav, u }` in `SYNC_LISTS` (item-level
merge, newer `u` wins, tombstones for removals); `touchChip` on block start (one chip per preset + name, moved to the
front, recents capped at 6; favourites up to 12, pinned first); `toggleFav`; `loadChip` loads the name and the preset
(a chip whose preset is gone is not shown; a direct load of one loads the name only and drops it); `clearRecents` asks
first, keeps favourites, Undo restores; Enter / Space / F on a focused chip; the loaded chip is marked. The legacy
`recent` / `pinned` arrays migrate once (`chipsFromLegacy`, in `hydrate`, in `applyProfile` when neither side has chips,
and on import) and are still written for clients before v1.18 (derived from the chips). `pushProfile` now keeps the
edit pending until the cloud copy has been read. Tests: `v118a`.
### 1b. Challenge join cap
`CH_JOIN_MAX = 1`: your own challenge plus at most one joined challenge a week. Client: `joinedThisWeek()` counts the
week's challenges you are a member of but did not create (and the counter doc); the header card shows "Joined this
week: n/1"; the Join button becomes a disabled "You're already in a challenge this week". Server: `challengeJoins/{uid}`
`{ weekKey, n, last, at }` must be written in the same batch as the join (`getAfter` both ways): the join rule requires
the counter to name this challenge and week, the counter rule allows n = 1 only (a new week resets it, the same week
must step by exactly one and name a different challenge), the named challenge must list me as a member after the
batch and not be mine, owner-only read, no list, no delete. A client before v1.18 (no counter in its batch) is refused
with the usual "Couldn't join" toast. People already over the cap keep their challenges (the client counts
memberships, so they cannot join more; the server counter starts at 0 for them, which is the one case the rules
cannot see). Tests: `v118b` (client + 6 rule attacks).
### 1c. FOUND ON THE WAY — clan creation broken in production since 1 November 2026 (rules)
`raidHPFor` called `raidRange(mk)` three times; from November the 12-month branch is live, and the six-document
clan-creation batch exceeded the Firestore rules engine's 1,000-expression budget ("Unable to evaluate the expression
as the maximum of 1000 expressions to evaluate has been reached"). Reproduced on the emulator with the v1.17 rules
(empty database, any account): `clanCreate` fails; with the fix it passes. Fix: the range and the clamped member
count are bound once with `let`. The first clan contribution of each month evaluates the same function once inside a
smaller transaction, so contributions most likely kept working, but the fixed rules should be published as soon as
possible. (The rules file also carries the v1.18 challenge counter, so publishing it alone is safe for v1.17 clients
except that they can no longer join challenges until they update — see the report.)

## Phase 2 — design (sessions without a clan, reusing the clan live engine)
- **One engine, two homes.** The live engine keeps its state (`LIVE`, `S.timer.live`) and gains a path layer: `liveRef()`
  = `clans/{cid}/live/{lid}` when `S.timer.live.cid` is set, else `studySessions/{lid}`; `people/{uid}` and
  `reactions/{uid}` hang off either. Every `FB.doc(FB.db, 'clans', LIVE.cid, 'live', LIVE.lid, …)` goes through
  `liveDoc(...sub)`. `liveMine()` = host (or clan officer for clan sessions). Group credit (`liveMaybeCount`) and the
  clan feed stay clan-only. After a join the app opens the Clan tab (clan session) or Friends › Study sessions.
- **`studySessions/{sid}`** `{ title, host, hostName, pattern{focus,short,rounds}, mode:'together'|'synced', startAt,
  pausedAt, pauseTotal, shift, open, counted:false, vis:'friends'|'link'|'public', lobby:'public'|'friends'|'none',
  max 2–10, members:[uids] (host first, ≤ max), invited:[friend uids ≤ 100] (friends-only lobby), plan: ms or 0,
  hostAt, code (8 chars, link visibility), createdAt, endedAt, updatedAt }`. `sessionCodes/{code}` → `{ sid }` (get only).
  Lobby queries (no composite index): public = `where('lobby','==','public')`; friends = `where('invited',
  'array-contains', me)`; closing sets `lobby:'none'`, `invited: []`, `open:false`. Sessions older than 6 h count as
  closed everywhere and anyone may close them (rule), hosts' "End" closes, the last one out closes (as clans).
- **Joining.** Public and invite-link sessions: self-join (`members: arrayUnion(me)`) while `open`, `members.size() <
  max`, `vis in ['public','link']`; the link is `?session=CODE` (captured like `?clan=`), the code resolves through
  `sessionCodes`. Friends-only: "Ask to join" creates `studySessions/{sid}/requests/{uid}` `{ name, at, status:'pending' }`
  (own uid, friend of the host, one per person, a new request only 60 s after the last); the host answers (status
  'ok' / 'no'); 'ok' adds the uid to `members` in the same batch (`getAfter(request).status == 'ok'`); the requester
  cancels (delete); requests older than 2 min are ignored (client timeout). Host popup: a held-safe toast + an inbox
  item with Allow / Decline actions during focus (never a dialog). Presence writes (`people/{me}`) need `me in members`.
- **Host.** Kick = `members: arrayRemove(uid)` + delete their people doc (host only); hand over = `host` set to a
  member (host only), or by any member when the host's presence beat is older than 2 min / state 'left' (the
  longest-present member does it); if everyone leaves the session ends. `hostAt` tracks tenure.
- **Invites.** Friends: `inbox/{uid}/items/sinv_<me>_<sid>` `{ type:'sinvite', sid, title, createdAt }` (rules extended)
  with Join / Ignore in the inbox and a toast; strangers: the link, copy via `copyText`, regenerate / disable the code
  (`code: ''`).
- **Friends tab** gets three views: Friends (list, status, "Studying now" + "Ask to join" on hosts of open sessions),
  Study sessions (host form, live now, planned, history from `S.sessions` entries with `sess`), Challenges (moved, cap
  shown). Session blocks are logged with `{ live: lid, sess: 1, mates: [uids who focused at the same time] }` so Phase 3
  can count "2+ present and focusing" minutes from overlapping presence.

## Phase 3 — rewards for studying together
- **What counts.** A block counts as "together" only when someone else's presence at the same table said "focus"
  while I focused (`s.mates`, from the heartbeats; up to 12). A solo "group" session has no mates and earns nothing.
  Hosting is recorded per block (`hs`); the last round of a Synced session with 3+ people sets `syf`. Everything is
  derived from the synced session log (`groupStats()`, cached by the log's length and last block), so every device
  agrees and nothing new is stored. Import keeps the new block fields.
- **Coins** (in the coin ledger `earnedAt`, so they replay identically everywhere): a new study partner +10, at most 3
  new people a day; a block in a clan session with someone +2, at most 10 a day.
- **Bonus Clan Points**: a clan-session block with a clanmate gives 1 point per 25 minutes (1 for 15–24 minutes), at
  most 6 a day per member. The member row keeps the day and the count (`bday`, `bcp`); the clan keeps `bonus`, which
  counts in `clanEarned` (spendable in the clan shop). Rules: `memberBonus` (own row, day not ahead of the calendar or
  back in time, count only grows, ≤ 6) and `clanBonus` (the clan total grows by exactly the row's increase); `earned()`
  includes `bonus`. Both fields are optional; old clients ignore them.
- **Achievements** — 21 "Together", 5 "Clan" milestones, 13 "Garden"; existing ones get categories (Focus, Streaks,
  Shop). Rewards are real items: titles (Host, Table Host, Study Buddy, Social Scholar, Campus Legend, Clan Scholar,
  Five-Star Farmer, Market Regular), auras (Kindred, Clan guard, Storm, Bloom), frames (Linked, Clan banner), avatars
  (Study duo, Star crop), a room poster (Together), a ring style (Orbit), stamps (Full table, Night shift, Clan crest),
  reward-only garden decor (Picnic blanket, String lights, Sundial, Harvest trophy, Windmill), two clan-exclusive
  species (Clan clover, Clan rose — never in a shop, the rotation or the daily slot), produce, seeds and eggs.
  `giveAchReward` gives each reward once under a fixed id (two devices give the same ids; a device that missed one
  gets it on the next reconcile). Achievement produce is a garden-ledger entry (`src: 'ach'`, capped at 100 each)
  that the purchase replay skips.
- **Clan milestones**: 5 / 15 / 40 / 100 / 250 hours of clan-session focus with a clanmate → 2 Clan clover seeds + 25
  coins, Clan crest stamp, Clan banner frame, Clan guard aura, Clan Scholar title + 2 Clan rose seeds. Shown on the
  clan page and on the profile (with "Studying together": hours, partners, sessions hosted).
- **Achievements page**: category filters, sorting (by category / closest to done / completed first), a progress bar
  on every unfinished one, the reward named on each.
- Found while testing: the new clan frame first reused the id `frame_clan`, which already belongs to the clan-level-4
  "Clan shield frame" — renamed `frame_g_banner` (and every new id checked for clashes). The clan page showed the
  summary of a session without a clan — now only clan summaries there.

## Phase 4 — design (streak milestones)
- Milestones 3 · 7 · 14 · 30 · 50 · 100 · 200 · 365 days (the brief's numbers). Claimed in `S.game.claims.milestones`
  (the existing add-only, synced map; 3 / 7 / 30 / 100 were already claimed by existing users and keep their coins).
  Judged on the longest streak from `computeStreaks` (which already uses the per-day goal history from v1.17), so a
  goal change can't re-award or break anything; a broken and rebuilt streak never pays a claimed milestone again.
- Rewards scale (coins rise at every step): 3 → 15 · 7 → 40 + title "On a Roll" · 14 → 60 + title "Unbreakable" ·
  30 → 200 + the Ember theme · 50 → 300 + the Flame Pomeo picture · 100 → 750 + the Hundred-day trophy (room shelf) +
  the Flame ring · 200 → 900 + the Blaze frame (animated) · 365 → 1,500 + the Eternal flame aura + the Golden Pomeo
  statue (room corner).
- Celebration: a skippable dialog (flame, the day count, the rewards) through `holdForFocus` so it never interrupts a
  block; several milestones reached at once (an update, an import) show one dialog listing them. Next milestone and
  progress on the profile and under the streak on the Timer.
