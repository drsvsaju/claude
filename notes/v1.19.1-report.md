## 1. Bug: "Focus time" opened the Ranks board
**What you saw:** after a visit to Ranks (or Streaks), clicking **Focus time** stayed on the Ranks "This season" board,
or jumped back to it. A reload didn't help.

**The cause.** Each board button reopens the last period you used on that board. The app remembers one period per board:
`lbFocusPeriod`, `lbGardenPeriod`, `lbRankPeriod`, `lbStreakPeriod`.
- The render function filed the period correctly under all four boards.
- The click handler was written when there were only two boards (v1.16). It kept only two cases: garden periods went to
  Garden, and everything else went to Focus.
- So clicking **Ranks** stored `season` as the Focus period, and clicking **Streaks** stored `streak`. The Focus time button
  is drawn as `data-period="<the Focus period>"`, so it then carried `season` and opened Ranks.
- The bad value is part of the saved UI state, so it survived a reload.
- I reproduced it on the v1.19 build, clicking Ranks, then Focus time, then reloading and clicking Focus time again. Each
  time the result was still Ranks · This season, and the Focus button held `season`. The fixed build opens Focus time ·
  Weekly in both cases.

This is the same family as the v1.18 Friends switcher bug: a switcher's state written by two code paths that disagree.

**The fix.**
- One function (`setBoardPeriod`) now files a period under its own board, and both the click handler and the render
  use it.
- A board button now says which board it opens (`data-kind`). The handler reads that board's remembered period when
  clicked, instead of trusting a value baked into the button.
- A remembered period counts only if it belongs to that board. Saved state that 1.19 corrupted (for example `season`
  stored as the Focus period) is repaired on read, so users who already hit the bug are fixed automatically.
- An unknown saved scope or clan-board period falls back to the default.

**Other switchers checked.** I looked at every other switcher in the app (14), both in the code and with a click-through
test:
- Stats, Friends · Study sessions · Challenges, Reminders · To-do · Flashcards, Boss · Questline, the Garden views,
  achievement categories, the inbox filter, and the Collection log filter;
- also the clan board period, the clan shop tabs, the to-do priority, the share-card size, the auth tabs and the session
  mode.

Each one stores a single value and has a single writer, so none has this bug. I also checked every class toggle in the
app that might receive an undefined value, the cause of the v1.18 bug; all of them receive true/false.

## 2. The Monthly focus board is gone

  app versions still on someone's phone keep their Monthly board.

  app versions. Leave it in place; it costs nothing.

## 4. Switchers: one line, a pill the size of the selected button
**What you saw:** the Achievements category bar (All / Focus / Streaks / Together / Clan / Garden / Shop) wrapped onto two
lines. The selected tab's highlight stretched to the full height of the wrapped bar, a large blob. At 360 px the bar ran
over three lines and the highlight was 104 px tall, against 35 px for a button.

**The cause.** Every switcher in the app shares one sliding-pill routine (`syncSegs`).
- The pill was styled `top: 3px; bottom: 3px`, so it always spanned the bar's whole height. It only ever moved sideways
  (`translateX(offsetLeft)`).
- That works for a bar on one line. Three bars were allowed to wrap: the Achievement categories (`.seg-wrap`) and two
  leaderboard rows (`.lb-head .seg`, `#lbKind`). For those, the pill took the height of all the lines and sat at the top.
- The pill was also measured only when a class or the window size changed, not when a button changed size (fonts, a
  different theme).

**The fix: one shared change for every switcher, with no per-screen patches.**
- **Never wraps.** A bar that doesn't fit its space scrolls sideways:
  - no visible scrollbar, and smooth scrolling (instant with animations off);
  - the selected option is scrolled into view when chosen, when the bar is redrawn, and when the bar changes width or
    becomes visible;
  - a soft fade on the side (or sides) that has more options.
- **The pill takes the selected button's own box**: its left, top, width and height, exact to the sub-pixel. It uses the
  button's layout box, so the brief shrink of a pressed button doesn't throw it off. Because the pill sits inside the
  bar, it follows the bar when it scrolls.
- **Measured again** whenever a bar or its selected button changes size (`ResizeObserver`). That covers fonts, themes,
  Glossed Interface, and a view drawn while hidden and then shown. It is also measured on window resize, on theme / glass
  / minimal / animation / font-size changes, and when web fonts finish loading.
- **Two layout fixes it needed.** On the Profile, the Achievements bar sits inside two grids. A grid column grows to fit
  its widest content unless told otherwise, so the one-line bar stretched the column past the screen instead of
  scrolling. Columns of `.grid-2`, and the Achievements toolbar, may now be narrower than their content.
- **The phone's bottom bar** keeps its own small pill design and only follows sideways, as before.

**Every switcher checked.** The new test reaches 21 switchers, plus the welcome page's, and checks each one:
- Stats, Friends · Study sessions · Challenges, and the session mode;
- Reminders · To-do · Flashcards, Boss · Questline, and Solo / Squad;
- the Garden views and the achievement categories;
- the leaderboard scope / board / period, and the clan board period;
- the inbox filter, the Collection log filter, the to-do priority and the share-image size;
- in the demo, the clan screen, the clan shop tabs and a friend's page;
- on the welcome page, the sign-up / log-in tabs and the phone bottom bar.

Before the fix, only the achievement categories wrapped at these widths. The leaderboard rows had the same weakness
whenever they ran out of room. All of them now go through the same code. The shop's category row (`.catrow`) already
scrolled and has no pill.

## 5. Wide screens: balanced card columns
**What you saw:** on the Clan and Profile pages, one column of cards ran out and the other kept going, with a big empty
area beside it. Measured in the demo at 1440 px:
- **Profile:** the Achievements card was one 5,552 px column beside 2,445 px of other cards, so the columns ended 3,072 px
  apart.
- **Clan:** the columns ended 520 px apart.
- **Timer:** the columns ended 275 px apart.

**The cause.** Each page put its cards into two fixed columns written into the page (left stack, right stack). How tall
each column ends up depends on your data (how many achievements, members or milestones you have), so one side often ran
much longer. On Profile, a single card (Achievements) was taller than everything else combined, so no arrangement of the
existing columns could balance it.

**The fix: one shared layout (`.mason`) for every multi-card page.**
- **One list of cards in reading order, most important first.** On wide screens the browser splits the list into two
  balanced columns (CSS columns). A card is never cut in two. The split re-flows by itself when a card opens or closes, on
  resize, and when the sidebar collapses.
- **When two columns can't be balanced** (one or two cards, or one column would end more than 160 px above the other),
  the list becomes one centred column, at most 760 px wide, instead of leaving one side blank. It goes back to two
  columns by itself when they would balance again. A small check (`fitMason`) does this, re-run whenever the list or any
  card in it changes size or cards are added or removed.
- **Phones and tablets (under 860 px):** one full-width column, in the same order as before.
- **Pages.**
  - **Profile:** the cards are balanced. The Achievements card now runs full width below them, with its list in
    columns, so it is about a third as tall.
  - **Clan:** the order is live session, join requests, planned sessions, members, quest and raid, activity, clan session
    milestones, trophy case.
  - **Quests:** the order is boss, rewards to claim, squad, battle log, rewards, next boss.
  - **Friends.**
  - **Timer:** the timer stays top-left and the Session card stays under it. The other cards balance around them. The
    Timer page never falls back to one column. Zen mode and the focus dimming work as before.
- **Other pages checked:**
  - **Garden, Stats, Shop, Reminders, Leaderboard and Settings** have no side-by-side card columns, so nothing could end
    early.
  - **Bag:** its left panel is sticky (it moves with the page) and was left as it is.
  - **Very wide screens (1920, 2560 px):** the page content is capped at 1,040 px and centred, as before.
- Result in the demo at 1440 px: Profile columns now end 77 px apart, and Clan 67 px.

## 6. Bug: a study session with a long preset was refused ("…refreshing your clan")
**What you saw:** hosting a non-clan study session with the preset "Brutal locked" (240 / 5 × 4; Focus together, Friends
only, 6 seats, start now) failed with the toast "That isn't allowed (or something changed) — refreshing your clan".

**The cause: two separate problems.**
1. **The rules.** The study-session rules (`validPattern`, v1.18) reused the clan range for a session's rhythm:
   - focus 5–120 min, break up to 30 min, up to 8 rounds.

   The app's preset editor allows:
   - focus 1–240 min, short break 1–120 min, up to 12 rounds.

   So any preset with a focus block over 120 min (or under 5), a break over 30 or more than 8 rounds was refused. "Brutal
   locked" has a 240-minute focus block.

   I reproduced it in the emulator with the exact rules published for v1.19: the 240-minute session was refused, and a
   25-minute one started.

   I checked every other field the session write sends (title, host, mode, visibility, lobby, seats, invited list, plan,
   link code, timestamps), as well as the seat (presence) document written right after. All of them match the rules.
2. **The message.** Every study-session button ran through the clan helper (`clanAct`). On any refused write it said
   "refreshing your clan" and reloaded the clan, even for a session that has nothing to do with a clan.

**The fix.**
- **One table of preset limits** (`PRESET_LIMITS`: focus 1–240, short break 1–120, long break 1–180, rounds 1–12) drives:
  - the preset editor's inputs;
  - a check before a session is written;
  - the rules, which now accept exactly that: focus 1–240 whole minutes, break 1–120, rounds 1–12.

  That keeps a firm maximum. A session table can still be closed by anyone after 6 hours, as before, so a very long
  preset doesn't leave a table open forever.
- **Before writing:**
  - A preset outside that range (for example from an old backup) gets a clear message before anything is sent: "Study
    sessions support focus blocks of 1–240 min — pick a preset in that range".
  - The host form shows the same warning.
  - Values are sent as whole numbers.
- **Session buttons have their own helper (`sessAct`).** Each refused action says what happened, for example:
  - "Couldn't join — the session may be full or closed";
  - "Couldn't let them in — the request may have been withdrawn or the table is full";
  - "Couldn't start the session — please try again".

  A refused write reloads the session list, not the clan. Clan actions keep the clan message and the clan reload.
- **If the app arrives before the rules** (`index.html` uploaded before the rules are published), a long preset gets "Couldn't
  start a session with this preset — try one with focus blocks of 5–120 min, breaks up to 30 min and up to 8 rounds". It
  never shows the clan message.
- **Clan sessions are unchanged.** They only offer fixed patterns up to 90 min, which their own rules already accept.

**Older app versions.** The rule only widens the accepted range. 1.17 to 1.19 only ever wrote sessions inside the old
range, so their writes still pass. A 1.18 or 1.19 app reading a longer session made by a 1.19.1 user just runs its timer:
I checked that code for any 120-minute assumption and found none.
