## What must hold in every commit
- The app is deployable: `index.html` parses, the affected suites pass, older accounts load.
- Existing users keep everything. New fields are optional with safe defaults. Apps 1.18–1.20 keep working against
  the new rules (they write `publicProfiles`, `publicStats`, `rankStats`, `activity`, `presence` as whole documents,
  so v2.0 never depends on new fields surviving there).
- The demo never writes (no Firestore writes, no browser storage changes) and shows every new feature.
- Firebase config: the live values stay (authDomain `pomodorolist-bbaa6.firebaseapp.com`).
- No PWA pieces (no manifest, no service worker, nothing that caches `index.html`).
- No real money, no fake urgency, no shaming copy, no dates of birth, no contact scraping.

## How the work is organised
- **One writer.** Only one agent (or I) edits `index.html` at a time. Planning, design drafts, reviews and audits run in
  parallel; code changes are applied one after another, with the affected suites re-run after each.
- **Workflows, medium-sized** (under 10 agents), used where parallel or independent eyes add quality:
  design directions with a judge panel, screenshot critiques by reviewers who see only the pictures, code review and
  rules attack review with a second agent trying to refute each finding, audits, the long simulations.
  Small single-reader jobs run as one agent or inline.
- **Usage limits.** A workflow that hits a limit is resumed, not restarted. A phase is never left half-applied: if a
  limit looms, the current step is finished, tested and committed first.
- **Tests** run from the scratch harness (copy in `tests/`); suites never run concurrently (a run clears the emulator).
- **Screenshots:** `tests/shots.mjs` shoots the same named screens for before and after (60 screens × desktop dark,
  desktop light, phone; `deviceScaleFactor: 2`). After each phase: 6–10 pictures to the owner with captions,
  before/after pairs stitched side by side, all committed under `screenshots/v2.0/<phase>/`.
- **Design loop per major screen:** build → shoot desktop + phone → list at least 5 concrete problems as a strict
  product designer → fix → reshoot, twice; then an independent reviewer agent that sees only the screenshots.

## What the maps found (the facts the design rests on)
Sources: `notes/v2.0-codemap/01…05`, `07-js-function-index.md`, `notes/v2.0-audit-controls.md`,
`notes/v2.0-audit-visual.md`.
- **Themes are JS palettes.** `applyTheme()` writes nine variables inline on `<html>` (`--bg --surface --text --muted
  --line --accent --accent-soft --heat0 --on-accent`) from `SKINS`. Anything that must follow a theme either derives
  from those nine in CSS (`color-mix`) or is added to every palette. Tests compare some of these values exactly.
- **Tokens exist but are not used.** v1.7 defined `--sp-1..6`, `--r-sm/md/lg/pill`, `--sh-1/2`, `--fs-xs..xl`; about
  5% of declarations use them. In the wild: 26 radii, 50 different shadows, 27 font sizes (42 half-pixel), 109
  distinct paddings, 20 transition durations, 255 hex literals.
- **Contrast fails today:** white on the accent is 3.91:1 (light) and 2.52:1 (default dark) on primary buttons,
  active segments and pills; warning text 3.46:1; control borders 1.26:1.
- **Motion switches are global:** Off kills every transition/animation with `!important`; Reduced allows only
  opacity/colour transitions. New components must work in both.
- **Stacking:** modal `<dialog>`s are in the top layer; Glossed gives cards and dialogs `backdrop-filter`, which makes
  them containing blocks for fixed children. Popovers must use the top layer (`popover` attribute) or be portalled the
  way `toastHost()` does.
- **Ids are the API.** About 60 controls are wired once at load by `$('#id').addEventListener`; code reads `.value` /
  `.checked`, sets them programmatically and rebuilds `<option>` lists with `innerHTML`. A missing id stops the script.
- **Modal state** is `document.querySelector('dialog[open]')` in 10+ places (shortcuts, the focus guard, tours,
  toasts). Sheets therefore stay real `<dialog>`s; open popovers are reported to the focus guard explicitly.
- **Settings DOM shape** (`.set-sec > h2 + .setting[data-k]`) is read by the settings search, the command palette, the
  row-toggle code and the demo lock: regrouping keeps that shape.
- **Rules:** 30 match blocks, 18 indexes, a 1,000-expression budget already hit twice. New server state goes in new
  documents. Rules can prove server-clock facts only (when a document was created, time between writes); minutes are
  self-reported everywhere. `users/{uid}/**` is owner-only, so private v2.0 data needs no rules change.
- **Tests that drive native controls:** 17 `selectOption` calls in 8 suites, `fill()` on date/time inputs, 47 suites
  answer native dialogs, 11 stub `window.confirm`. A shared test helper comes before the swaps.

### 1c Component library (namespace `UI`, section "UI LIBRARY (v2.0)" in the script + one CSS section)
Design rule: **enhance, keep the native element as the value holder.** The original element keeps its id, `.value` /
`.checked`, `disabled` and its `input`/`change` events, hidden from sight and from the tab order; the custom control
mirrors it both ways (programmatic `.value =` sets and `innerHTML` option rebuilds included). A single observer
enhances controls that templates insert later. If the library fails, the native control still works.

### Visual direction
Three directions were drafted as standalone prototypes (Timer screen + component sheet, desktop + phone, dark + light,
two palettes) and judged by two reviewers who saw only the screenshots: **A "Soft depth" 7.6 / 7.0**, B "Quiet ink"
6.8 / 6.5, C "Warm garden" 6.3 / 7.5. A won and was refined with both reviewers' objections and the best of B and C
(`notes/v2.0-design/reference/`, `notes/v2.0-design-direction.md`; the three drafts are kept beside it).

What the app takes from it:
- **Shape language.** A pill is something you press, a square well is something you type in or choose from, a rounded
  sheet is a surface. Radii: 6 labels, 8 wells and rows, 12 panels, 16 cards, 22 the hero card, dialogs and sheets.
- **Depth, not borders.** Layers from deepest to nearest: frame (header, sidebar), stage, quiet card, card, hero card,
  panel. Each is a tone, a top highlight and a shadow; one hero per view; one filled accent button per view; nothing glows.
- **Contrast is arithmetic.** The script works every colour role out of a palette's nine colours (`derivedFor`), so
  the promises hold in all 40 palettes × light/dark and on every layer: a field's lip and a button's edge 3:1, the
  focus ring 3:1, secondary / accent / status text 4.5:1, text on a filled button 4.5:1. `v200a` measures them all.
- **Never colour alone.** A switch's knob reads O / I, a chosen segment gets a ring, a tint and bold text, a
  destructive confirm carries a warning tile and a verb.

Where the app deliberately differs from the reference prototype:
- The prototype is drawn on solid surfaces. The app's default look stays **Glossed · Lite** over the time-of-day
  sky (it is part of the personality); the layers become translucent there and keep their highlight and shadow.
  Glossed Off shows the solid reference look; True Minimalist stays plainer still.
- The prototype mixes colours in CSS (`color-mix`, relative colours). The app does the same arithmetic in the script
  and writes plain values, so older browsers (iOS 15) get the same colours, and contrast can be *searched for* per
  palette rather than hoped for. The stylesheet carries the default palette's results as generated literals.
- Dialogs and phone sheets are opaque in every glass level (a translucent dialog takes the scrim's colour and ends up
  greyer than the page it covers).
- The controls are custom elements with the native contract (`<ui-select>`, `<ui-date>`, `<ui-time>`, `<ui-num>`,
  `<ui-color>`, `<ui-tags>`: `.value`, `.options`, `.disabled`, one `input` + one `change` per user action, labels via
  `for=`), not a hidden native element enhanced in place. Swapping a tag is then the whole migration of a call site,
  and nothing can drift between two copies of a value. Older suites drive them through `tests/ui-compat.mjs`.

### Phase 3 — what was done

### Phase 4 — what was done

**How it was measured.** `tests/perf4.mjs` drives the read-only demo, as it is (239 sessions) and as a large account
(`tests/tools/bigacct.js`: 2 years / 2,815 sessions, 413 harvests, 50 friends, 40 clan members, 150 posts, 120
reminders, 240 to-dos, 800 flashcards), on a laptop window and a phone, at full speed and with the processor
throttled 4×. It records start-up, every tab switch (median of five, to the next frame), the slowest interactions by
the browser's own Event Timing (what INP is made of), frame rate, DOM size. `tests/tools/prof.mjs` wraps every
top-level function to show where the time goes. The machine has no GPU, so every frame is drawn by the processor:
blur and repaint costs show as they do on a weak phone.

**Found and fixed, by cause**
- *Blur.* A blurred surface re-blurs what is behind it in every frame in which anything moves. The Timer had nine
  blurred cards (2 million px² on a laptop) and a full-screen blurred navigation scrim that was painted at opacity 0.
  In the default look a card has only the soft colour wash behind it, where a 10 px blur changes no pixel (compared
  before/after: 0.00–0.03 % of pixels differ, at card edges). Cards and tiles keep their translucent fill and lose the
  blur; the top bar, the bottom bar, the drawer and pop-ups (which float over content) keep it; "Extra glossy" keeps
  blurred cards. The closed scrim is `visibility: hidden`.
- *The ring.* It was redrawn 60 times a second for an arc that moves 0.6 px a second in a 25-minute block; each redraw
  repainted the Timer card. It is redrawn when it has moved a third of a pixel.
- *Dialogs.* The scrim behind a dialog blurs the whole page, and 47 endless animations kept producing frames behind
  it. The page stands still while a dialog is open.
- *Forced layouts.* Progress bars were started one by one, with a layout of the whole page for each (76 ms on the
  Profile); list entrances likewise (40 ms on the Bag). One layout each now.
- *Saving.* Every tab switch and every view or filter choice rewrote the whole account to local storage on the spot
  (10–14 ms on the large account) and threw away the derived numbers. The choice is stored 0.4 s later, and at the
  latest when the page is left; a change to the account still saves at once.
- *Twice.* The clan's rank arriving drew the whole Profile a second time for one line; it redraws its own card.
- *Off-screen tiles.* Item tiles (Bag, Shop, Almanac) and achievement rows that are off screen are skipped by the
  browser (`content-visibility`), with a margin so nothing of theirs is clipped. Tried on plain rows too (to-dos,
  friends, posts): opening got faster but scrolling at 4× throttle fell from 60 to 29–35 frames a second, so it was
  taken back there.
- *Long lists.* To-dos, reminders, friends, posts, clan members and leaderboards write their first 40 rows and keep
  the place of the rest (so the page has its final height and nothing jumps); the rest is written in idle moments,
  normally within a few frames. Lists of ordinary length are written exactly as before.
- *The year heatmap* animated 365 cells one by one and built a date formatter for each: 53 week columns and one
  formatter.
- A bug of phase 3 found on the way: animations stilled during a focus block with `pause()` and resumed with `play()`
  no longer obeyed the stylesheet, and kept looping after Animations was set to Reduced or Off. They are stilled by
  their speed now.

### Phase 5 — what was done

**5a. All-day reminders**
- *Data:* an optional `allDay: true` on a reminder. `time` stays a valid HH:MM (the alert time it was saved with), so an

  (older versions drop a reminder whose `time` is not a string, and split it on ":"). Turned off again the field is

- *When it alerts:* `S.settings.allDayAt` (optional, 8:00 when missing or broken), a row in Settings → Notifications.
  From that time until the day ends, so opening the app at 3 PM still alerts ("or on first open that day"). One key
  per day (`id@day@allday`) in the same fired-once guard as timed reminders, so changing the alert time after it rang
  does not ring it again and a second device stays quiet; a snooze rings under its own key as before.
- *Where it shows:* "All day" in the time column, leading its day in Today and Upcoming; a line of its own in the Today

  planned focus block is a reminder with `kind: 'block'` and `dur` (minutes), both optional; an older version of the

- *What a day shows:* its items (timed ones with their time, all-day ones first), and its focus as a tint that

- *Planning:* "+ Plan a block", a click on an empty hour, or a drag over empty hours in the Week (quarter hours)
  open the block form with that day, start and length; when the block is due its reminder comes up and "Start now"

  scrolls. Every move says what it did, with Undo. Repeating reminders, sessions, exams and finished to-dos do not
  drag (which occurrence would move?). The keyboard's way is the item's own form (its date and time fields).
- *One day:* a click on a day, Enter on it, or "+N more" opens the day: everything in it as rows, and Focus block /

- *Export:* one `.ics` with what is still ahead (reminders and blocks with their repeat rules, open to-dos with a due

## Phase 6 — focus features (each optional, skippable, never during a running block)
Private data lives under `users/{uid}` (session records for per-block data; `users/{uid}/extra/*` documents, read
when their screen opens, for notebooks). Shared features get their own collections with rules and attack suites.
1. **Intention + debrief:** one-line intention before; after the block, done (yes/partly/no) + focus 1–5; stored on
   the session record; history, Insights; one tap to skip; a setting.
2. **When-and-where plans:** "I'll study ⟨subject⟩ at ⟨time⟩ at ⟨place⟩" → a planned block + reminder.
3. **Fresh starts:** new week / month / event card with a recap, one slightly bigger goal, a nudge 2–3 days later.
4. **Healthier streaks:** weekly rest day, pause mode (≤ 7 days, limited per month), earned freezes (compatible with
   the existing ones), 48-hour repair quest (once a month), graduation at 100 days, rewritten copy. Streak maths stay
   derived from the session log, with the new allowances as dated, synced records.
5. **Friend Streaks:** `friendStreaks/{a_b}`, integer UTC day marks, own mark only, one step a day, up to 5 (client
   cap); shown on friend rows, profiles, Posts.
6. **Buddy Quest:** `buddyQuests/{week_a_b}` (a new collection: older apps crash on unknown challenge presets),
   shared progress bar, reward through the local claim ledger.
7. **Strict mode** (off by default): leaving the tab > ~15 s wilts the block's focus sprout (minutes still count, the
   bonus is lost); warning first, grace and a "screen locked" allowance, honest limits; optional table Pact.
8. **Insights:** best time of day, best block length, subject balance vs the plan, rating trends, interruptions,
   overtime; relative stats only from already published data; weekly insight card.
9. **Ambient mixer:** generated sounds only (rain, café, library, white/brown noise, fireplace, forest), per-preset
   defaults, fades, quiet-during-focus respected.
10. **Resume card**, 11. **Distraction tally**, 12. **Break activities** (breathing, stretch, 20-20-20, water).
13. **Mistake notebook** and **mock test tracker** (private, synced, exportable, linked to flashcards).

### Phase 6 — design notes written while phase 5's regression ran (nothing applied yet)

**6a. Intention, debrief, distraction tally, resume card** — drafted as `tests/drafts/phase6a/` (patch + suite); it
applies cleanly to a copy of `index.html` and the result parses.
- The intention is device-local with the timer (`S.timer.intent`), the logged block keeps it as `int` and the tally
  as `dx` (session records are written once, by `arrayUnion`, so anything known at the end of the block rides there).
- The answer comes later, so it is a map in the profile like the focus check-in: `debrief { sessionId: 1 | 2 | 3 }`.
- The focus rating stays the existing 4-step check-in. The brief asks for 1–5; older versions keep only 1–4 and
  would drop a 5, and two scales would split the insights. Reported as a deviation.
- "Yes" clears the intention; "partly" / "not yet" keep it for the next block. The resume card shows only when you
  come back (20 minutes to 3 days after a block that left something open).

**6b. Healthier streaks** — one helper decides whether a day keeps a streak alive without adding to it
(`streakKept(day)`: a freeze, the weekly rest day, a pause, a repaired day), used by `computeStreaks`,
`useStreakFreezes` (a freeze is never spent on a rest or paused day) and the weekly recap. New optional maps in
`S.game` (Firestore's merge keeps nested keys an older version does not send, and the app unions these maps):
- `rest { fromDay: weekday | -1 }` — the rest day in force from a date, so the past is never re-judged; a change
  applies from tomorrow and at most once a week (it cannot rescue today after the fact).
- `pauses { startDay: days 1–7 }` — today or later, at most 7 paused days a calendar month, can be ended early.
- `repairs { missedDay: ts }` — written when the 48-hour recovery (2× the daily goal after exactly one missed day,
  for a streak of 3 or more) is done; once a calendar month. Derived from the session log, so two devices agree.
- Freezes stay as they are: bought with coins, and coins come only from focus (the brief's "earned, never bought
  with money" already holds). Graduation at 100 days: a permanent mark and quieter copy. Kept days never add to a
  count, so nothing published (streak boards, ranks) can be inflated and no rule changes.

## Risks
| risk | mitigation |
|---|---|
| A redesign of a 23,000-line single file breaks behaviour quietly | one writer; affected suites after every step; DOM hooks the suites use are kept; full regression at phase ends |
| Restyling by regex flips cascade results (appended fix-up blocks, glass `:is()` lists, duplicate keyframes) | tokens added as a layer; values migrated per section with eyes and screenshots |
| Custom controls drift from the values the code expects | enhance-and-mirror design; a mirroring test per control; ids unchanged |
| Popovers clipped or under dialogs; invisible to the focus guard | top layer + portal fallback; sheets are real dialogs; guard flag |
| 21 palettes × light/dark × Glossed × Minimalist × 3 motion levels | tokens derived from the nine variables; a contrast suite over all palettes; the gallery shot in a sample matrix |
| Rules budget (1,000 expressions) and older clients | new collections only; older clients never see new presets or inbox types; attack suite per collection |
| Document size / reads on Spark | per-block data on session records; notebooks in lazily read documents; usage measured before/after |
| Tests that drive native controls (selectOption, native dialogs) | a shared helper first; suites updated with each swap |
| Usage limits pause the work mid-phase | small steps, each tested and committed; workflows resumed |
